# 0.6 배포 컴파일의 저장 위치 호환성

검토·수정일: 2026-11-09. 원본과 모든 증거는 `D:\CampusRomance_VN` 아래에 있다.

## 확인된 문제

이전 `launcher_publish/prepare_payload.py`는 매번 `native_snapshot`을 지우고 모든 RPYC를 제외한 새 원본으로 컴파일했다. Ren'Py의 자동 문장 이름은 시간과 일련번호를 포함한다. 이전 RPYC를 읽을 수 없으면 같은 대사도 새 이름을 받으므로, 대사가 그대로라는 비교만으로 저장된 실행 위치의 호환성을 보장할 수 없다. 이전 테스트가 RPYC 없이 다시 만든 구버전 원본에서 시작한 경우 실제 배포본 저장과 같은 이름을 검증한 것도 아니다.

설치 업데이트가 세이브 파일 자체를 지우지 않는 것과, 업데이트된 실행 코드가 그 저장 위치를 정확히 찾는 것은 별개다. 이번 수정은 이 후자의 배포 문제를 해결한다.

## 공식 SDK 동작 확인

수정한 SDK는 없다. 실제 설치된 Ren'Py 8.5.3.26051504 원본을 읽었다.

- `tools/renpy-8.5.3-sdk/renpy/script.py:536`: `assign_names`는 새 자동 이름에 `int(time.time()*100)`과 일련번호를 사용한다.
- 같은 파일 `:556`: `merge_names`는 옛/새 AST의 `diff_info()`를 비교해 일치하는 문장의 이름을 이식한다.
- 같은 파일 `:866~879`: 새 RPY를 읽을 때 대응하는 기존 RPYC slot1을 읽어 `merge_names`한 뒤 `assign_names`한다.
- `renpy/ast.py:866`: Say의 `diff_info()`는 화자와 대사 내용을 포함한다.
- `renpy/arguments.py:54,205`: `compile` 명령은 자체적으로 모든 RPY의 강제 재컴파일을 활성화한다. 원본 RPYC를 새 코드 대신 그대로 배포하는 방식이 아니다.

## 공개 0.5.2 컴파일 원본 보존

삭제나 재빌드 전에 아래 경로에 버전별 append-only 원본을 보존했다.

`launcher_publish/compiled_seeds/2026110901/`

- 실제 공개 `0.5.2-test / build2026110901`의 게임 RPYC **58개·1,289,317바이트**.
- 공개 원문 `manifest.json`, detached `manifest.sig`와 성공한 `activation_receipt.json`.
- 각 파일의 경로·크기·SHA256과 manifest/서명/활성화 영수증 해시를 기록한 `SEED_RECORD.json`.
- 공개 manifest SHA256: `251579548fd70c47d99609cf85b16866df8061f1c89f8309bb50ba1ff9f334e1`.

58개 파일 모두 공개 manifest의 크기·SHA와 일치한다. manifest는 런처가 사용하는 고정 공개키로 .NET RSA/SHA256 서명을 검증했다. 개인 서명키나 게시 토큰을 읽거나 복사하지 않았다. 예전에 보고된73은 publisher의 RPY/JSON 원본 해시 개수이며 실제 공개 게임 RPYC 개수와 구분한다.

이 경로는 기존 파일을 덮어쓰지 않는다. 재사용할 때도 manifest 서명·활성화 근거·각 파일 해시를 다시 검증하며 변조나 누락은 빌드 전에 거절한다. 원본 공개 snapshot은 QA 담당자가 별도 구버전 fixture로도 확보했다.

## 수정한 배포 흐름

`launcher_publish/prepare_payload.py`의 변경 범위는 컴파일 원본 사전 보존·검증·설치와 빌드 검사 기록이다. 기존 아이콘 교체, 실제 게임 원본 보존, 사설 파일 제외, 조각 생성 절차를 유지한다.

1. 마지막 **성공한 실제 활성화 영수증**의 build·manifest SHA를 기준으로 삼는다.
2. 해당 버전의 보존본이 있으면 다시 검증한다. 없다면 로컬 manifest/서명과 기존 공개 snapshot이 활성화 영수증에 정확히 일치할 때만 처음 보존한다.
3. 새로 준비하거나 서명했지만 아직 게시하지 않은 후보는 공개 버전으로 간주하지 않는다. 후보가 여러 번 만들어져도 이전에 검증한 실제 활성 버전의 보존본을 사용한다.
4. 보존본이 없는데 로컬 후보가 공개 영수증과 다르거나 snapshot 해시가 맞지 않으면, 기존 snapshot을 지우기 **전에 실패**한다. 다른 디렉터리의 RPYC나 개발 원본을 임의의 대체품으로 사용하지 않는다.
5. 새 원본 RPY를 generated snapshot에 복사한 뒤, **새 RPY가 존재하는 같은 경로**의 옛 RPYC만 복사한다. 삭제된 원본의 오래된 RPYC를 고아 모듈로 살려두지 않는다.
6. 수정하지 않은 공식 SDK의 `compile --keep-orphan-rpyc`를 실행한다. 기존 이름은 공식 `merge_names`로 보존하고 실행 내용은 현재 원본으로 강제 재컴파일한다.
7. `payload_audit.json`의 `compiled_seed`에 근거 build/SHA, 복사한 파일, 제거된 원본 때문에 제외한 항목과 공식 컴파일 방법을 기록한다.

개인 플레이 기록은 보존본이나 공개 payload에 포함하지 않는다. 전체 ZIP이나 새 설치 프로그램을 만들지 않는다. 보존본 검증은 공개키만 사용한다.

## 실제 컴파일 이름 대조

실제 공개 보존본에서20개 원래 route의 RPYC를 가져와 현재 RPY와 같은 경로에 배치했다. 별도의 D 드라이브 최소 프로젝트에서 공식 SDK 강제 컴파일을 실행한 뒤, 옛/새 slot1 AST의 같은 Say `diff_info()`와 자동 이름을 대조했다. 비교용 프로그램은 실제 SDK에서 실행했고 compiler를 대체하거나 패치하지 않았다.

| 조건 | 비교 route | 같은 화자·대사 문장 | 옛 이름 유지 | 이름 불일치 |
| --- | ---: | ---: | ---: | ---: |
| 공개 RPYC를 미리 배치한 새 컴파일 | 20 | 11,305 | **11,305** | **0** |
| 같은 새 원본을 RPYC 없이 컴파일한 대조군 | 20 | 11,305 | **0** | **11,305** |

따라서 이전 배포 방식의 이름 변경을 실제로 재현했고, 공식 보존 절차가 같은 대사의 이름을 유지함도 확인했다. 옛 임시 시아 제작 중 안내3문장은 새 정식 루트 연결로 대체되어, 옛 Say11,308개 중 새 원본에 그대로 있는11,305개가 비교 대상이다. 새 시아 S01/S02는 이전 공개 버전에 없던 파일이므로 대응 RPYC가 없고 새로 컴파일한다.

이 검사는 **저장 위치로 사용되는 대사 이름**을 직접 검증한다. 모든 가능한 저장 시점의 Ren'Py 실행 문맥까지 이 검사 하나로 보장했다고 주장하지 않는다. 실제 공개 구버전의 대사 중간 세이브를 새 seeded candidate에 불러오는 네이티브 검사는 별도 QA 담당자가 수행한다.

증거: `tests/relationship_overhaul_060/compiled_seed/seeded_result.json`, `unseeded_result.json`, `header_seed_install.json`.

## 사전 보호 검사

별도 QA 디렉터리에 복사한 공개 메타데이터로12개 보호 검사를 수행했다.

- 아직 게시하지 않은 다른 로컬 후보가 있어도, 검증한 활성 버전의 보존본만 재사용.
- 보존본이 없고 로컬 후보가 다르면 snapshot 처분 전에 거절.
- 보존 RPYC 변조, 서명된 manifest와 다른 snapshot, 활성화 영수증의 build 불일치 거절.
- `..`, 역슬래시, 드라이브 문자, 저장 폴더 등 위험하거나 사설인 manifest 경로 거절.
- 새 RPY가 있는 항목만 복사하며 고아 RPYC는 복사하지 않음.
- 실제 게임 원본·SDK·기준 runtime을 복사 대상 snapshot으로 지정하는 실수 거절.

모두 통과했고 실제 공개 보존본·기준 runtime·SDK·사용자 세이브를 변경하지 않았다. 결과: `tests/relationship_overhaul_060/compiled_seed/guard_checks.json`.

## 운용 주의

- `compiled_seeds`와 마지막 활성화 영수증을 임의로 정리하지 않는다. 큰 그림 파일의 캐시와 다른 저장 호환 근거다.
- 버전을 실제 게시한 뒤에는 그 버전의 manifest/서명과 RPYC도 보존해야 한다. 다음 `prepare`의 삭제 전 절차가 이를 수행한다. 게시 직후 `published_compiled_seed()`를 호출해 먼저 고정해도 된다.
- 보존본이 없고 snapshot도 공개 manifest와 달라졌다면 빌드를 강행하지 않는다. 공개 manifest/서명과 해당 조각에서 RPYC를 복구하고 동일 해시를 검증해야 한다.
- 원고에서 대사나 실행 파일 경로를 실제 삭제·변경한 경우까지 이름이 그대로 유지된다고 보장하지 않는다. 이번 공통/로만 원고의 보존된 문장은 직접 대조했다.

수정 전 publisher는 `tests/relationship_overhaul_060/compiled_seed/prepare_payload.before.py`에 보관했다. 시험의 최초 메타데이터 직렬화 오류는 probe의 버전 문자열 호출을 고쳐 해결했으며, 초기 실패 로그를 별도로 남겼다. 제품 SDK나 배포 후보 코드의 오류가 아니고, 최종 두 공식 컴파일 실행은 모두 종료 코드0이었다.
